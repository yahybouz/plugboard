# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Old data is now purged automatically** (PLU-32). **Before upgrading, back up `data/`**: rows older than the retention are deleted for good at the first pass, so with the defaults usage older than 13 months and audit entries older than a year disappear the first night. A retention pass runs inside the server every day at `PLUGBOARD_RETENTION_HOUR_UTC` (`4`, UTC) and deletes the usage entries older than `PLUGBOARD_USAGE_RETENTION_MONTHS` whole months (`13`), audit entries older than `PLUGBOARD_AUDIT_RETENTION_DAYS` (`365`), watchdog events older than `PLUGBOARD_WATCHDOG_RETENTION_DAYS` (`14`), availability snapshots older than `PLUGBOARD_MONITORING_RETENTION_DAYS` (`90`) and chat sessions expired after `PLUGBOARD_SESSION_TTL_S`, then compacts each store when at least 20 % of its pages are free. `0` keeps a store's rows for ever; a negative value or one that is not a whole number gives the default. `PLUGBOARD_RETENTION_DISABLED=1` turns the daily pass off. The last report is written to `data/retention.json` and returned by `GET /admin/retention` (admin) with the settings in force; a pass that deleted rows records a `retention.run` audit line. Rows are deleted in short batches (5000 rows, each in its own transaction, 50 ms apart), so billing, watchdog and session writes get through during a long purge. The Jobs page lists the pass as *Data retention*, with **Run now**; a pass that leaves a store in error (locked or corrupt) shows as an error there, naming the store, while the other stores are still purged ([data retention](docs/guide/configuration.md#data-retention)).
- **Availability snapshots are taken on a schedule** (PLU-34): every active provider is probed every `PLUGBOARD_MONITORING_INTERVAL_S` seconds (`300`) and the result is stored in `data/monitoring.db`, where the Monitoring page computes uptime; a probe that does not answer within 30 seconds counts as down. `0` turns the snapshots off and a value from `1` to `59` gives `60`. The Jobs page lists them as *Availability snapshots*, with **Run now**.
- **`GET /health/ready` says whether the instance can serve requests** (PLU-31): a public route that answers `200` when ready and `503` with the same body (`ready`, `version`, `checks`) when not. It blocks on `usage_db` (`data/usage.db` cannot take a write lock), `cli` (the binary of an active CLI provider is missing from PATH, without starting it) and `auth` (`API_KEY` empty outside `PLUGBOARD_DEV=1`); it reports `ollama` (from the watchdog's last checks, no network call) and `background` (watchdog, availability snapshots, retention pass) without ever blocking on them. The result is kept 5 seconds and concurrent calls share one evaluation; the body names no provider and carries no error text. Container and deployment probes stay on `/health` ([health endpoints](docs/guide/monitoring.md#health-endpoints)).

### Changed

- **Breaking: the public `GET /health` shows only the status and the version** (PLU-31, BUG-58): its body is now exactly `{"ok": true, "version": "…"}`. The fields `providers`, `active`, `auth_disabled` and `dev_mode` are removed: the list of providers is on the admin `GET /providers`, and the client authentication posture is `checks.auth` of `GET /health/ready`, which answers `503` when `API_KEY` is empty outside dev mode. A deployment gate that read `auth_disabled` on `/health` must move to `/health/ready`. `/health` still answers `200`, so container and deployment probes are unchanged, and it no longer reads any file. The dashboard overview counts the active providers from `GET /providers`. API contract 2.0.0: `GET /health/ready` is added, its `503` described by the `Ready` body, and `Health` keeps `ok` and `version` only ([health endpoints](docs/guide/monitoring.md#health-endpoints)).
- **Opening the Monitoring page no longer records a snapshot** (PLU-34): `GET /admin/monitoring` used to store its own health check, so uptime measured how often an admin opened the page. It now stores nothing and computes uptime from the scheduled snapshots only; with no snapshot in the period, `uptime_pct` is `null` (shown as `—`) instead of `100`.

### Fixed

- **A manual usage purge can no longer reach the current month** (PLU-32): `POST /admin/usage/purge` accepted `keep_months=0` or a negative value, and a negative value deleted the current month's usage along with every older month. A `keep_months` below 1 is now refused with `422` and nothing is deleted; `plugboard.usage.purge_old_usage` raises `ValueError` for such a value.

## [4.11.5] — 2026-11-12

- **Debian fixes published after the Python base image are now applied** (`api` and `full` images): the `base` stage runs `apt-get upgrade`, which stays on the image's Debian release and only updates installed packages; `zlib1g` moves to `1:1.3.dfsg+really1.3.1-1+deb13u1` (CVE-2026-76844, CVE-2026-85091, HIGH). Node stays on 22; `npm` and `npx` move to a new major version.

## [4.11.4] — 2026-11-12

### Fixed

- **A client key issued under the client ID `admin` still acted as the administrator** (BUG-60, D-40): 4.11.1 stopped creating such keys, but one issued earlier was still served as the administrator (no `allowed_models`, budget, unknown-price `402` or `rpm_limit`, every call in `GET /v1/inflight`). A key whose `client_id` is `admin` in any case, with or without surrounding spaces, is now refused like a key with a blank client ID: the same `401` as an unknown key on every route that takes a client key, nothing called or billed, a warning `reason=reserved_client_id` with its `key_id` (never the key). `GET /admin/keys` still lists it; rotating it is refused with `422`. `ADMIN_KEY` and the dashboard session are not affected. This replaces 4.11.1's "existing keys are not changed". **Before upgrading**, look in `GET /admin/keys` for keys whose `client_id` is `admin` in any case or with surrounding spaces (`GET /admin/keys/client/admin` finds only the exact `admin`) and reissue them under another client ID: a key named `Admin` or ` admin ` was an ordinary client key that kept its limits and worked until now, and is refused too.

## [4.11.3] — 2026-11-12

### Fixed

- **A client key issued with a blank `client_id` still escaped the key's limits** (BUG-64, D-40): 4.11.2 stopped creating such keys, but one issued earlier with the `client_id` `""` kept skipping its `allowed_models`, budget, `rpm_limit` and billing. Such a key, or one whose `client_id` is only spaces, is now treated as an invalid key on every route that takes a client key (chat v1 and v2, preflight, models, embeddings, decisions, `/v1/me`, `/v1/me/keys`, `/v1/inflight`, and `/usage/me`, which the client portal reads with `/v1/me`): the same `401` as an unknown or revoked key, and nothing is called or billed. A warning with its `key_id` (never the key) is logged on each refusal. `GET /admin/keys` still lists it; rotating it is refused with `422`: revoke it and create a new key with a client ID. This replaces 4.11.2's "existing keys are not changed". **Before upgrading**, look in `GET /admin/keys` for keys whose `client_id` is empty or only spaces and reissue them: a key whose `client_id` is only spaces kept its limits and worked until now, and is refused too.

## [4.11.2] — 2026-11-12

### Fixed

- **A client key could have a blank `client_id`** (BUG-64): `POST /admin/keys` accepted the `client_id` `""`, and the chat routes read an empty `client_id` as "no caller": with such a key, `POST /v1/preflight` skipped the key's `allowed_models`, `monthly_limit_usd`, `rpm_limit` and the `402` for a model without a known price, and recorded no usage; `POST /v1/chat/completions` did the same when `PLUGBOARD_ALLOW_PERMISSIVE=1`, and shared its cached answers with every caller without a client ID (in the default strict mode it answered `401`); `GET /v1/models` listed every model whatever the key's `allowed_models`. An empty `client_id` or one made only of spaces is now refused with `422`, like `admin`; nothing is written. The dashboard form never sent it. Existing keys are not changed: a key created this way keeps its empty `client_id`, also when rotated, and keeps escaping those limits on these routes; find it in `GET /admin/keys` (empty `client_id`), revoke it and issue a new one under a real client ID. A `client_id` made only of spaces escaped nothing.
- **An unparsable custom endpoint address got a `500` from the connection test** (BUG-63): `POST /admin/direct-providers/test` with a `base_url` whose IPv6 bracket is not closed (`https://[x`) or holds a name (`https://[x]/v1`), or whose host name has an empty label or a label over 63 characters (`https://api..example.com/v1`), answered `500`, and one whose port is out of range or not a number was tried and reported *Unreachable*. Such an address is now refused with `422` *base_url refused: not a valid address*, like the route's other unusable `base_url`; nothing is called. A models.dev catalog entry with such a port no longer breaks the preset list: that entry is left out, like a non-public one.
- **A catalog preset whose name has no letter or digit could not be added** (BUG-65): since BUG-61 a provider id made from the name must not be empty, and a preset's name cannot be edited, so `POST /admin/direct-providers/catalog-<id>` for a models.dev provider named only in another script (or with symbols) answered `422`. The id is then made from the preset key (for example `catalog-acme`) and the name is kept as it is; a name with a letter or digit still gives the id, as before. A name typed in `POST /providers` or the MCP `add_provider` tool is still refused with `400`.

## [4.11.1] — 2026-11-12

### Fixed

- **A client key could be named `admin`** (BUG-60): `POST /admin/keys` accepted the `client_id` `admin`, and the gateway takes a key's `client_id` as the caller's identity, so such a key was treated as the administrator on the chat routes: no monthly budget, no `402` for an unknown price, no `rpm_limit`, no `allowed_models`; the administrator's response cache; provider error details, busy provider IDs and `X-Price-Key`; every call in `GET /v1/inflight`. `admin`, in any case and with surrounding spaces, is now refused with `422`, like the route's other invalid fields; nothing is written, and the dashboard's **Create key** form shows the refusal instead of reporting a key created. Existing keys are not changed, and rotating one keeps its `client_id`: look for them with `GET /admin/keys/client/admin`, revoke them and create keys under another client ID.
- **A provider could be saved with an empty id** (BUG-61): the id is made from the name's letters and digits (a-z, 0-9), so a name such as `!!!`, blank or written only in another script gave the id `""`, and `POST /providers` saved it. Such a name is now refused with `400` before anything is written, like the route's other refusals; the MCP `add_provider` tool shows that refusal.
- **An invalid provider address got a `500` from the egress guard** (BUG-62): with *Public addresses only* ticked, a `base_url` whose host name the IDNA codec rejects (a label over 63 characters, an empty label, a non-ASCII character it forbids), whose port is out of range or whose IPv6 bracket is not closed raised an error the guard did not catch: `500`, and no `provider.egress.rejected` line in the audit. On `POST` and `PUT /providers` it is now refused with `422` *Provider base_url refused* and audited, like an internal address. A catalog preset with such an address now gets `422` *Catalog preset refused* before a connection test or a creation (these routes write no audit line).

## [4.11.0] — 2026-11-12

### Added

- **MCP admin tools: `add_provider` and `refresh_catalog`**: a coding agent can add an OpenAI-compatible provider and refresh its model list without the dashboard. They are off by default: they need `PLUGBOARD_MCP_ADMIN_TOOLS=1` and `PLUGBOARD_ADMIN_KEY`, run over stdio only (SSE and HTTP never load the admin key) and refuse when the gateway enforces admin MFA. They call `POST /providers` and `POST /providers/{id}/discover`, so the gateway's checks, audit and webhooks apply; `add_provider` creates the provider inactive, with *Public addresses only* on, so an internal address is refused and no client traffic reaches it before an admin activates it; `refresh_catalog` refuses CLI providers. Limits per MCP process: 5 `add_provider` calls per hour, one refresh per provider and mode per minute, one at a time. The tools never show the provider key back and the gateway never audits it; the MCP SDK's DEBUG message logs are dropped. The gateway records these calls with the actor `mcp` (header `X-Plugboard-Surface: mcp`): `provider.create`, `provider.discover`, `provider.egress.rejected`, `provider.domain.rejected`, plus the other refusals (`provider.create.refused`, `provider.discover.refused`) and previews (`provider.discover.preview`); the dashboard's entries are unchanged. `POST /providers/{id}/discover` also answers `first_population`. MCP contract 1.5.0 ([guide](docs/guide/mcp.md#admin-tools-stdio-only)).

## [4.10.0] — 2026-11-12

### Security

- **MCP update registry tools act for the calling key's client only**: `check_updates`, `list_applied`, `mark_applied`, `get_update_prompt` and the `updates://pending` resource took the client from a `client_id` argument, so any caller could read another client's pending updates and their instructions, or mark them applied in its place. The client now comes from `PLUGBOARD_API_KEY`, through `GET /v1/me` at each call, over stdio, SSE and HTTP. `client_id` becomes optional and is refused when it names another client; an update for another client answers *not found*, and no other client's name is shown. The registry tools, and `inflight_requests`, refuse an MCP server started without a client key or with the admin key. MCP contract (`docs/api/mcp.json`, 1.5.0): `client_id` is optional in `check_updates`, `list_applied` and `mark_applied`. **Upgrade:** `clients` in `registry.json` must be a list holding the client IDs of your keys; an update recorded as applied under another name shows as pending again ([guide](docs/guide/mcp.md#update-registry)). An MCP server shared by several projects now serves only the client of its key: run one per client ([network transports](docs/guide/mcp.md#network-transports-sse-http)).

### Added

- **Ollama switch** (PLU-12): Ollama can be turned off or on at once, without a restart or a redeploy, from the **Available to the API, MCP and Playground** switch on the Ollama page or `GET`/`PUT /admin/ollama/switch`. It sets the `ollama` provider's **Active** field, saved in `providers.json`. Off, its models leave `/v1/models` and `/v2/models` (so the MCP `list_models` tool and the Playground), a chat request for one of them gets `503` with `code` `provider_disabled` and a `hint`, `POST /v1/preflight` reports `provider_disabled`, embeddings answer `503`, and nothing calls the daemon: not the boot check, not the semantic cache. Calls already running go to their end; calls waiting for the Ollama slot get the `503` when their turn comes or when their wait ends. Turned back on, from the switch or the Providers page, the model list is synced once. A change made with the switch is audited as `ollama.switch` (state before and after, calls running and waiting); one made on the Providers page is audited as `provider.update`, which now records the `is_active` value. `OLLAMA_ENABLED` stays a startup setting. API contract 1.6.0.
- **Catalog history per provider**: which models a provider gained or lost, and when, was only visible as the last 20 changes of every kind in the Monitoring card. `GET /admin/catalog/history` lists model-list changes newest first, filtered by `provider`, `since` and `until` (UTC days, both included) and `model` (part of a name, any case), with `limit` (1 to 200, default 50) and `offset`; it answers `422` for an invalid value. Admin only, outside the client API contract. The dashboard gets a **Catalog history** page (one card per change, the first 10 names then **+N more**, names matching the model filter first and highlighted, **Load more**, readable at phone width) and a **Full history** link under Monitoring › Recent automatic changes. The change journal (`data/catalog/changes.jsonl`) now keeps changes for `PLUGBOARD_CHANGE_JOURNAL_DAYS` days (365, `0` = no age limit) and at most 10 000 lines, instead of its last 1 000 lines of every kind ([guide](docs/guide/monitoring.md#catalog-history)).
- **A running chat call is visible on every surface**: a slow call (a CLI starting for 5 to 13 s, a large Ollama model for minutes) looked the same as a hung one. `GET /v1/inflight` lists the calling key's chat calls in flight, each with its model, the surface that sent it (`api`, `playground` or `mcp`, from the `X-Plugboard-Surface` header), the time elapsed, its phase (`waiting_slot`, `running`, `waiting_provider`, `cli_queue`, `cli_running`, `cli_parse`) and a `slow` flag after 60 s, then the last 20 results with their HTTP status. The MCP server gets an `inflight_requests` tool, and the dashboard a corner pill (calls in flight, click for the list) and a ticking status line in the Playground. The admin sees every call with its provider through `GET /admin/inflight`; a client key never sees another key's calls or the routing. Nothing is stored: the list lives in memory and holds no prompt or answer. API contract 1.5.0.

### Changed

- **The dashboard follows a written design system**: [DESIGN.md](DESIGN.md) lists the color, type, spacing and radius tokens shared by the admin dashboard, the client portal and the ticket board, and every page now uses only these tokens: 27 font sizes become 7, 32 spacings a 9-step scale, and inline styles become named classes (the ones scripts toggle stay). `tests/test_dashboard_design_tokens.py` keeps raw values, undefined variables and old labels out. Labels follow one rule: US English, sentence case (*API keys*, *Usage & billing*, *Add direct provider*), *Log out*, and `…` for work in progress. `/suivi` is now in English, with the sidebar link **Tickets**; the status and type values of its API do not change and its server error messages are still in French. The client portal gets the dashboard layout (its header and key figures had none), follows the light or dark system setting instead of forcing dark, and draws its chart with the palette. The Ollama **Delete** button is red as intended. No behavior changes.

### Fixed

- **A disabled provider's model went to the other providers** (BUG-44): a request for a model of a provider turned off (`ollama:qwen3:8b`, or a name only that provider lists) was sent to every other active provider in turn, so a prompt meant for the local model reached cloud providers, and a preflight pinged and billed them. It now gets `503` `provider_disabled` and nothing is called, on the chat routes (v1, v2, streamed or not, MCP and Playground included) and the preflight; the routing core refuses it for every other caller too. A key's `allowed_models` is checked against the real owner; no cached answer is served for such a model. One exception remains: while an active provider has no model list (a custom endpoint never discovered), a bare name such as `qwen3:8b` is still sent to the active providers, since that one may serve any name; the `ollama:` prefix is always refused.

## [4.9.0] — 2026-11-11

### Security

- **Protected providers connect to public addresses only**: the base URL of a provider created from the models.dev catalog comes from a third-party feed and was checked only when the provider was created or tested, so if its host name later resolved to an internal address (DNS rebinding: `127.0.0.1`, `10.x`, `169.254.169.254`...), Plugboard sent the provider's key and the prompts there. Catalog presets, built-in presets with an HTTP(S) URL, and custom endpoints with the new **Public addresses only** box ticked (`egress_guard`, off by default) are now checked at every connection: a host name with one non-public answer, an IP address written in the URL and a redirect target are refused before anything is sent. The periodic model probe (`POST /api/generate`) of a ticked `sovereign` endpoint whose name contains `ollama` is checked the same way: its models show `egress_refused`. A refused request goes to the next candidate provider, or answers `502` when there is none; the provider stays active and the circuit breaker does not count the refusal. The first refusal per provider in any 5 minutes is recorded in the audit log as `provider.egress_refused` and sent to `ALERT_WEBHOOK_URL` as `provider_egress_refused` ([payload](docs/guide/monitoring.md#alert-webhook)). A new base URL on a protected provider, or ticking the box, must be a public `http(s)` address (`422`, audited as `provider.egress.rejected`); a base URL sent back unchanged is not checked again, and `egress_guard: false` is refused on catalog and built-in presets. `GET /providers` returns `egress_guard` and `egress_guard_forced`; the Providers page shows the box (ticked and greyed out on presets) and a **public only** badge, and a failed creation from the form now shows its error instead of *Provider created*. The connection test of a catalog or built-in preset no longer follows redirects. Protected providers now ignore `HTTPS_PROXY` and connect directly: behind a mandatory proxy, or for a preset whose base URL was pointed by hand at an internal address before this release, add a custom endpoint to the same URL with the box left unticked. Ollama and unticked custom endpoints are unchanged ([guide](docs/guide/providers-and-subscriptions.md#public-addresses-only), [outbound network](docs/guide/deployment.md#outbound-network)).

### Added

- **A provider takes a limited number of requests at once**: a local provider (`sovereign`, a `base_url` on a loopback or private address, or an Ollama reached over plain `http://`, whatever its host) now takes one request at a time by default (`PLUGBOARD_LOCAL_PROVIDER_MAX_INFLIGHT`, `0` restores 4.8.0), and any provider takes at most its `max_concurrency` when its record sets one. Every request holds a slot on its provider while it runs, streamed or not, CLI included, and gives it back when it ends, fails or the client hangs up. A non-streamed request for a model without provider prefix goes to the next candidate when one is full; a streamed request still has a single route and waits for that provider only, even when another candidate is free. A full provider counts neither against its circuit breaker nor as an error.
- **A request waits for a free provider, then gets `503 providers_busy`**: when every candidate provider of a chat request is full (for a streamed request, its single provider), the request waits up to `PLUGBOARD_PROVIDER_WAIT_S` seconds (default 10, `0` answers at once) for the first freed slot, oldest request first, and is then answered `503` with `"code": "providers_busy"`, `retry_after` 5 and `Retry-After: 5`, without any provider call; the admin key also gets the ids of the busy providers. A client that hangs up while it waits leaves the queue at once. `POST /v1/preflight` reports such a pair with the error `providers_busy`, and the internet-access check (`POST /admin/models/check-internet`) answers `"status": "busy"` without recording anything, even with `"persist": true`. API contract 1.4.0 (the version that also adds the preflight's `model_not_found`, under Fixed): `providers_busy` in `ErrorResponse.code`, the `503` of both chat routes and the `error` of `PreflightResult`. A provider's `max_concurrency` (a whole number from 0 to 1000, `0` for no cap) can be set with `PUT /providers/{id}` ([details](docs/guide/providers-and-subscriptions.md#concurrent-requests-per-provider)). A protected provider whose address is refused (see Security) is skipped like a full one: when the next candidate stays full, the client gets this `503 providers_busy`, not `502`; the refusal is still audited and alerted.
- **A route that answered `429` is tried last for a while**: after a final `429` from an HTTP provider, streamed or not, or a quota error from a CLI, the route (provider and model) is paused for the `Retry-After` the provider gave, else for 30 s, then 1 min, then 5 min as its `429`s follow one another; a success clears it. A paused route, like a route whose circuit breaker is open, now comes after the other candidates of a model without provider prefix; it is never refused, and a route asked for by its prefix is still called. A key limited by `allowed_models` keeps the routes it may use when they go last or are full: it is answered `403` for another candidate only once those routes failed, as in 4.8.0.

### Changed

- **The load-balancing score counts every request in flight**: the in-flight part of the score that orders the candidates of a model without provider prefix (`PLUGBOARD_LB_INFLIGHT_WEIGHT`) only counted HTTP requests that were not streamed; it now counts streamed requests and CLI calls too, so the order of candidates for a model without prefix can change.
- **A long `Retry-After` is no longer waited out on the spot**: a `429` whose `Retry-After` exceeds the next retry delay (`PLUGBOARD_RETRY_DELAYS`) is not retried on the same provider any more; the next candidate, or the client, gets it at once instead of after about 22 s of retries. A `429` without `Retry-After`, or with a shorter one, is retried as before.

### Fixed

- **`PLUGBOARD_RETRY_DELAYS=inf` held a retried request for good**: the retry delays had their own reader, which refused text and negative values but let `inf`, `nan` and a number too large for a float (`1e999`) through. The first retry of a `429`, a `5xx` or a timeout from an HTTP provider then waited forever (`asyncio.sleep` of infinity or NaN never returns). A finite but huge delay (`1e300`, or `1e9`, about 31 years) held the request just as well. The list now goes through the shared reader (`envcompat.get_floats`): one item that is not a finite number of seconds from `0` to 7 days (`604800`, the cap already applied to a provider's `Retry-After`) gives the default `2,5,15`, with one warning naming the variable and the item. The format (comma-separated seconds, empty items skipped) and the default are unchanged. The test that keeps numeric settings on the shared reader now also follows a value through the variables built from it (`raw`, then `token`), which is how this reader escaped it.
- **The preflight pinged and billed a model no provider knows**: since 4.8.0 the chat routes answer `404 model_not_found` without calling any provider for such a model, but `POST /v1/preflight` did not apply the rule: a pair whose `<provider>:<model>` no provider knows (a mistyped provider ID, for example) was sent to the active providers in turn, as chat requests were before 4.8.0, and a ping one of them answered was billed. Such a pair now answers `"ok": false` with the closed code `"error": "model_not_found"`, for every caller (the admin key included), without a ping and without a usage line. The check comes in the chat route's place: after `budget_exceeded` and `forbidden_model`, so a key limited by `allowed_models` still gets `forbidden_model` and cannot learn which models exist, and before `price_unavailable` and the RPM count. A known model, a known provider prefix and a family alias `/v1/models` publishes are pinged as before. API contract 1.4.0: `model_not_found` added to the preflight's `error` codes ([details](docs/api/README.md#404-model_not_found)).
- **Two turns of one session sent together could lose one or answer without the other**: with a `session_id` (or the `X-LLM-Session-ID` header), a turn sent while the previous one was still being answered ran at once, without seeing it, and on a full history (`PLUGBOARD_SESSION_MAX_TURNS`) one of the two exchanges was lost when both were recorded. The turns of one session now run one after the other, in arrival order: a turn waits until the previous one is answered and recorded, and a client that hangs up while it waits leaves the queue (`499`) without calling any provider. Requests without a session, other sessions and the same session id under another client never wait, nor does a request refused by the checks (malformed `messages`, budget, allowed models, price, RPM limit): it is answered at once. The wait happens in one process, inside the chat request's concurrency slot (`PLUGBOARD_MAX_INFLIGHT_CHAT`).
- **A streamed turn was never recorded in its session**: with `"stream": true`, the answer of an HTTP provider or a CLI was not added to the session, so the next turn did not see it. An HTTP provider's stream is now recorded once it is complete, and an interrupted one is not. A CLI that exits on SIGTERM is stopped at once, and the version and sign-in checks use the same bounded stop.

A worker stuck in the kernel, or a child that left its group and kept the output open, made that wait endless: the decision only ended at the 45-second API deadline (504), and that cut left the inference lock and the single worker slot taken until a restart, so every later Laya call was refused with 429. The gateway now waits one second after SIGKILL, then logs a warning with the pid, frees the lock and the slot, and answers as usual.

### Fixed

- **Claude high load, model block and server throttling answered `429` quota**: claude sets `error: "rate_limit"` on more than the account's usage limit: on its Opus/Fable high-load switch ("is experiencing high load") and a per-model block, which it raises itself without an HTTP status, and on an API 429 it reports as "Server is temporarily limiting requests (not your usage limit)". The gateway read all of them as an exhausted quota and answered `429` "quota or rate limit exhausted" when no other provider could serve. They are now a provider failure: the other candidate providers are tried, then `502`. A usage or spend limit (`api_error_status: 429` and an `API Error` text or a usage-limit message) still gives `429`.
- **Circuit breaker blind to provider-qualified models**: `forward()` recorded failures and successes under the native model name but read the breaker under the model string the client sent, so a model asked as `provider-id:model` never saw its own failures. The native circuit it opened never closed again (`/admin/circuits` showed it open for good), and the LLM pricing pass, which reads `provider-id:model`, kept choosing a provider whose calls were failing. The breaker is now read and recorded under one key per route, `provider-id:model`; an unqualified model counts as open only when every provider it is tried on is. A request to an open circuit is still sent, as before.
- **Open circuit pinned other callers to one provider**: when every route of a model was open, the fallback rewrite looked for the `FALLBACK_MAP` entry as a substring of the native name. For a model whose fallback is a prefix of its own name (`gpt-5.5-pro` → `gpt-5.5`, `o3-pro` → `o3`, `qwen3.5` → `qwen3`…) it found the same model and narrowed the request to its first provider, so for 60 s no other provider was tried, even one that answered. Three requests refused for their own content (HTTP 400 "prompt is too long") were enough to trigger it for every caller. The rewrite now needs the model suffix to equal the fallback and no longer narrows a request to the model whose circuits are open.
- **A hung `<cli> --version` kept running**: the version check run at start-up (CLI warm-up), by the health watchdog and by the dashboard's CLI check gave up after its delay but left the CLI and its children running. They are now started in their own process group and killed with it when the delay runs out, as for a chat request. The check still gives up within two seconds of its delay when a child that left the group (a daemon) keeps its output open, so it can no longer stall the watchdog.
- **Exhausted TypeSafe quota answered 502 on `/v1/decisions`**: when TypeSafe answered HTTP 429 to a Jev decision, the client got the generic `502 Invalid decision engine response`. It now gets `429` as on `POST /v1/chat/completions` since 4.5.0: a reason written by the gateway naming `typesafe`, and TypeSafe's delay in `Retry-After` and `retry_after` when it gave one (at most 7 days). TypeSafe's body is never read nor returned, and nothing is billed. Other TypeSafe error statuses still answer `502` ([decisions](docs/guide/decisions.md)).

## [4.1.0] — 2026-10-22

### Upgrading

Defaults that change, and how to keep the previous behaviour:

| Change | To keep the previous behaviour |
|---|---|
| Prices and model lists refresh every 6 hours instead of once a day. | `PLUGBOARD_PRICING_REFRESH_INTERVAL_H=0` (and `PLUGBOARD_MODEL_AVAILABILITY_INTERVAL_H=0`). |
| Prices come from several sources (OpenRouter, models.dev, LiteLLM, built-in table). | Nothing to do if `PRICING_SOURCE_URL` is set: only `external,known` are used. Otherwise `PLUGBOARD_PRICING_SOURCES=litellm,known`. |
| A third-party price that moves by more than 20 % waits for review and is not billed until applied. | `PLUGBOARD_PRICE_DRIFT_ACTION=apply`. |
| Prices edited by an admin are kept (`source: manual`) instead of being overwritten by the next update. | **Revert to automatic** on the row, or `POST /admin/pricing/{month}/revert`. |
| The models.dev catalog is downloaded with each price update. | `PLUGBOARD_CATALOG=off`. |
| An automatic refresh removes a model only after two refreshes without it; a manual **Discover** removes at once. | `PLUGBOARD_MODEL_REMOVAL_PASSES=1` removes after one refresh. |
| Calls are billed with the price of the provider that served them (after fallback). | Remove `models_by_provider` from the grid. Run `make billing-reconcile` to see the difference on last month's usage first. |

Prices already in the grid without a `source` (written by an earlier update or an earlier `PUT`) stay under the automatic sources, as before: a source may still update them, but a change above `PLUGBOARD_PRICE_DRIFT_PCT` now waits for review. To freeze one, edit it once (it becomes `manual`). `PLUGBOARD_PRICING_SOURCE_URL` must now be https (http only for localhost). Existing providers keep `auto_discover` off: their model lists only change as before. The dashboard Pricing page now saves only the rows you changed.

### Added

- **Provider catalog from [models.dev](https://models.dev)** (MIT): every OpenAI-compatible provider it lists (OpenRouter, OpenCode Zen, Moonshot/Kimi, Groq, DeepSeek, Mistral, xAI, Together, Fireworks, DeepInfra, Cerebras and many more) becomes a one-click preset, marked *community, unverified*. The catalog is fetched with the pricing scheduler, validated entry by entry, and the last good copy is kept when the download fails or shrinks by more than half. `PLUGBOARD_CATALOG=off` (or an empty `PLUGBOARD_CATALOG_URL`) turns the outbound request off; `PLUGBOARD_CATALOG_URL` points to a mirror; `PLUGBOARD_CATALOG_EXCLUDE` hides providers. A provider created from a catalog preset keeps the base URL it was created with: a later catalog change never redirects its key.
- `POST /admin/direct-providers/test` checks a key against a preset or custom endpoint before anything is created (`ok`, `ok_no_models`, `invalid_key`, `not_openai_compatible`, `unreachable`).
- `make catalog-check` lists the presets generated from the live catalog.
- **Prices merged from several sources**, model by model, in the order of `PLUGBOARD_PRICING_SOURCES` (default `external,provider_native,models_dev,litellm,known`): your own document, OpenRouter's published prices, models.dev, LiteLLM, then the built-in table. Each grid entry records its `source`; a source that does not answer leaves its entries unchanged, and prices outside 0 to 1000 USD per million tokens (or with an output/input ratio outside 0.1 to 20) are ignored. If `PRICING_SOURCE_URL` is set and `PLUGBOARD_PRICING_SOURCES` is not, nothing changes: `external` then `known`, with a startup warning. `PLUGBOARD_PRICING_SOURCE_URL` is the new name of `PRICING_SOURCE_URL`.
- **Large price changes are held for review**: a change above `PLUGBOARD_PRICE_DRIFT_PCT` (20 %) from a third-party source waits in `GET /admin/pricing/suggestions` and is not billed until applied (`POST /admin/pricing/suggestions/{id}/apply|reject`, or in bulk with `{"ids": [...]}`). `PLUGBOARD_PRICE_DRIFT_ACTION=apply` writes them directly.
- `PATCH /admin/pricing/{month}` sets some prices without sending the whole grid, and `POST /admin/pricing/{month}/revert` gives a model back to the sources.
- **Automatic updates every 6 hours** for prices and model lists (`PLUGBOARD_PRICING_REFRESH_INTERVAL_H`, `PLUGBOARD_MODEL_AVAILABILITY_INTERVAL_H`; `0` keeps the daily run). Providers with `auto_discover: true` (catalog presets) are refreshed through `GET /models`; CLI providers at most every `PLUGBOARD_MODEL_AVAILABILITY_CLI_INTERVAL_H` hours (24). A model leaves a list only after two refreshes in a row without it, a refresh that would drop more than half of a list is not applied, and `default_model` / `pinned_models` are never removed. `POST /providers/{id}/discover` goes through the same rules and accepts `?dry_run=true`.
- **Change journal and webhooks**: `data/catalog/changes.jsonl` records every automatic change; `models.changed` and `pricing.changed` (`status: pending|applied`) webhooks, at most `PLUGBOARD_WEBHOOK_MAX_PER_RUN` (50) per update, never for a first population.
- `GET /admin/auto-update/status` groups both schedulers, the catalog, pending suggestions and recent changes; `POST /admin/auto-update/run` runs both now (`409` with `running_since` while busy). Scheduler statuses gain `stale`, `last_success_at` and, for models, `last_changes`.
- **Prices read by a model** (off by default, `PLUGBOARD_LLM_PRICING=1`): for advertised models that no source prices, once a day a model reads the provider's pricing page and its findings wait in the review queue; nothing is billed until applied. Hardened page fetch (https, exact host, pinned public address, no environment proxy, 2 MB), strict JSON answers, a daily budget (`PLUGBOARD_LLM_PRICING_MAX_USD`, 0.50) kept across restarts, calls billed to `plugboard-internal`. `GET /admin/pricing/llm/status`, `POST /admin/pricing/llm/run`.
- **Dashboard**: provider search with built-in and catalog groups, **Test connection** before creating a provider (with **Save anyway**), **Discovering…** state, `auto_discover` and pinned models in the provider form, discovery preview before removals; Pricing page with the automatic-update status, the **Needs your review** queue (apply or reject, one by one or in bulk), a searchable paginated grid with source filter, **Missing price only**, provider prices per model and **Revert to automatic**; an **Automatic updates** card and the recent changes on Monitoring; the price key and source of recent requests on Usage & Billing.
- **Prices per provider**: a grid can hold reseller prices in `models_by_provider` (filled automatically for OpenRouter, OpenCode, DeepInfra, Together and Fireworks when they differ from the vendor price). A call is priced with the provider that served it, after fallback, including streaming. Usage entries record `price_key` and `price_source`; admin keys get an `X-Price-Key` header. `make billing-reconcile` compares last month's costs with and without provider prices.

## [4.0.0] — 2026-10-18 — first public release

First public release of Plugboard, a self-hosted, OpenAI-compatible LLM gateway. The development history before this release is not published; this entry summarises what the release contains.

### Upgrading an existing install (LLM Enabler 3.x)

This release renames the project and changes several defaults. Before pulling it into an existing checkout:

0. **Start from a clean working tree**: `git status` must show no modified tracked file. Commit or copy aside local changes first; files removed by this release (internal docs, monthly pricing snapshots under `data/pricing/` that were tracked) disappear on pull.
1. **Back up local files that are no longer tracked**: `cp -a data data.bak`, and move the update registry: `cp docs/registry.json data/registry.json` (or set `PLUGBOARD_REGISTRY_PATH`). `git pull` stops if these files have local changes; restore them from the backup after the pull. Until moved, the registry is still read from `docs/registry.json`, with a warning.
2. **Start command**: the package is now `plugboard`. Use `python run.py` (or `uvicorn plugboard.app:app`); `llm_enabler` imports and `python -m llm_enabler...` no longer work.
3. **Environment**: `LLM_ENABLER_*` names keep working (deprecation warning); rename them to `PLUGBOARD_*` when convenient. A new name always wins over the old one.
4. **`ADMIN_KEY` is required**: the server refuses to start without it, or with fewer than 16 characters, unless `PLUGBOARD_DEV=1`. `LLM_ENABLER_DEV` is not carried over: remove it from production `.env` files.
5. **Dashboard**: the session cookie is renamed, so admins sign in once more. Auto-login only applies to a local install (`HOST=127.0.0.1`, or `PLUGBOARD_LOCAL_AUTO_LOGIN=1`).
6. **`/v1/models` lists every discovered model**; set `PLUGBOARD_MODEL_FILTER=curated` to keep the previous short list.
7. **Gemini OAuth**: set `GEMINI_OAUTH_CLIENT_ID` / `GEMINI_OAUTH_CLIENT_SECRET` if you sign in to Gemini from the dashboard or rely on automatic Gemini CLI token refresh.
8. **Integrations**: webhooks send `X-Plugboard-Event` / `X-Plugboard-Signature` (the previous header names are still sent for now); Prometheus metrics are named `plugboard_*` instead of `llm_enabler_*`; the Python SDK is `plugboard_sdk` with `PlugboardClient` (`LLMEnablerClient` stays as an alias); the MCP server is named `plugboard`. New client keys start with `pb_`; existing `lle_` keys keep working.
9. **Docker**: `docker compose` builds the slim `api` image (no provider CLIs); build the `full` target for CLI subscriptions.
10. **CLI providers get an allowlisted environment**: `claude`, `codex` and `gemini` no longer inherit the whole server environment. Credentials they need beyond their own (Bedrock or Vertex auth for `claude`, a custom CA bundle...) must be listed in `PLUGBOARD_SUBPROCESS_ENV_PASSTHROUGH`, comma-separated.
11. **Python SDK**: the package is now `plugboard_sdk` (`from plugboard_sdk import PlugboardClient`); `LLMEnablerClient` remains as an alias inside it.

### Gateway

- OpenAI-compatible API: `POST /v1/chat/completions` (with server-sent-event streaming), `GET /v1/models`, `GET /v1/models/benchmarks`, `GET /v1/models/{id}/info`, and `/v2` aliases.
- Models addressed as `<provider-id>:<model>`; retries with backoff on `429`/`5xx`, fallback across providers for unprefixed model names, latency- and error-aware ordering, per-model circuit breaker.
- Optional server-side chat sessions (`session_id`) and a global concurrency cap for chat requests.

### Providers

- API-key presets for Anthropic, OpenAI, Google Gemini and GitHub Models; custom OpenAI-compatible endpoints; Ollama detected and registered automatically, with model management from the dashboard.
- Subscription access through the official Claude Code, Codex and Gemini CLIs (run as subprocesses), through credentials stored by the Codex, Gemini and GitHub CLIs, and through GitHub's device flow. These modes may conflict with the providers' terms; see the README.
- Model discovery, daily account-aware catalog refresh, connectivity probes, quarantine of unavailable models, internet-access check.

### Clients, billing and pricing

- Per-client keys (`pb_` prefix; earlier `lle_` keys still accepted) stored as SHA-256 hashes, with monthly USD budget, requests-per-minute limit, allowed models and organisation grouping; revocation and rotation.
- Usage and cost recorded per request, client, key and month; `billing` object and cost headers in responses; CSV export; client self-service portal and `/v1/me`.
- Monthly pricing grids refreshed automatically by an in-process scheduler from a public price list or a custom JSON source, inherited from the previous month, editable in the dashboard; past months are never modified.

### Caching

- Exact-match response cache scoped per client; optional semantic cache with an optional embedding layer; cache replay for streaming CLI requests.

### Operations

- Admin dashboard: overview, keys, usage, providers, OAuth connections, pricing, playground, Ollama, monitoring, jobs.
- Health endpoints, JSON and Prometheus metrics, provider watchdog, health history, admin audit log, alert webhook for failing providers and spending, signed event webhooks, JSON logs with request IDs.
- MCP server with chat, model, usage and provider-status tools, and an update registry that tells client projects what to change.
- Docker image with the provider CLIs preinstalled; Docker Compose setup bound to `127.0.0.1`; Makefile targets for setup, development, tests and secret scanning.

### Security

- Dashboard auto-login limited to a local install opened in the local browser; `ADMIN_KEY` login with brute-force lockout and optional TOTP MFA elsewhere.
- Provider credentials, OAuth credentials and the MFA secret encrypted at rest; strict tenant isolation of caches by default; Content Security Policy and security headers; body size limits; per-IP and per-key rate limits; optional provider domain allowlist.
- Startup refused when `API_KEY` or `ADMIN_KEY` contains comment text copied from `.env.example`.
- CLI providers (codex, gemini, claude) run a client's prompt in isolation: an allowlisted environment instead of a copy of the server environment (`ADMIN_KEY`, `API_KEY` and `ENCRYPTION_KEY` never reach them; `PLUGBOARD_SUBPROCESS_ENV_PASSTHROUGH` for extra names), a private `0700` spawn directory, a codex permission profile that denies the rest of the disk, no user configuration, MCP servers, extensions or session history. gemini runs from a private `GEMINI_CLI_HOME` created per call: the operator's settings, memory, skills and MCP servers do not apply, and no gemini tool is exposed.
- Startup warning when `.env` is readable by the group or other users; `make init` creates it with mode `0600`.

### Configuration

- Environment variables use the `PLUGBOARD_` prefix; the previous `LLM_ENABLER_` prefix is still accepted and deprecated.
